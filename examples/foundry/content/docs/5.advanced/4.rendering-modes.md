## Overview

Foundry is a Nuxt 4 layer. It does not invent its own rendering pipeline — every URL flows through one of Nuxt's stock paths. Knowing which path a URL takes is the difference between a 200ms SSR'd marketing page and a 5MB SPA bundle shipped to a serverless function.

This page documents the resolution order, layout selection, and the rendering knobs the layer exposes. Contracts are backed by tests in `playground/test/e2e/rendering.e2e.spec.ts` — run them with `pnpm --filter playground test:e2e`.

## URL → page resolution order

For any URL, Nuxt checks in this order:

1. `app/pages/<exact-path>.vue` in your example app
2. `app/pages/<dynamic>.vue` in your example app (e.g. `[id].vue`)
3. `layer/app/pages/[...slug].vue` from Foundry — the content catch-all
4. 404

The catch-all calls `useContentPage()`, which uses `useContentConfig().getCollectionForRoute(path)` to pick a Nuxt Content collection (mapped via `app.config.ts` → `content.routeMap`), then fetches the document via Foundry's `/api/_foundry/content/page` server endpoint.

An `app/pages/foo.vue` always wins over a `content/pages/foo.md`. Use app pages when you need Vue logic; use content when you want non-developers editing the page.

## Layout selection

Nuxt picks a layout in this order:

1. `setPageLayout('x')` called from a component or middleware
2. `definePageMeta({ layout: 'x' })` on the page component
3. `routeRules: { '/foo/**': { appLayout: 'x' } }` in `nuxt.config.ts` — bridged by the layer's global middleware
4. The `default` layout

Foundry ships three layouts: `default`, `landing`, `article` (plus `docs` if the docs module is enabled). App pages can mount any layout without needing a sibling content file.

Content frontmatter `layout:` is **not** honored — set the layout via `routeRules.appLayout` instead.

## Content fetching

Catch-all → `useFetch('/api/_foundry/content/page')` → Foundry server endpoint → `@nuxt/content/server` → SQLite. Single code path, server-only. The client hydrates from Nuxt's payload. This is the boundary to extend if you want to add caching, auth, or rate-limiting around content access.

## Rendering modes

| Knob | Where | Effect |
|---|---|---|
| `ssr: false` (global) | `nuxt.config.ts` | Whole app is SPA — no SSR anywhere. Foundry default is SSR. |
| `definePageMeta({ ssr: false })` | page `.vue` | Per-route SPA. |
| `routeRules: { '/x': { prerender: true } }` | `nuxt.config.ts` | Bake to static HTML at build time. |
| `nitro.prerender.routes: ['/x']` | `nuxt.config.ts` | Same as above; explicit list. |
| `nitro.prerender.crawlLinks: true` | `nuxt.config.ts` | Follow `<NuxtLink>`s during build and bake every reachable URL. |
| `routeRules: { '/x': { swr: 3600 } }` | `nuxt.config.ts` | Stale-while-revalidate cache. |
| `routeRules: { '/x': { isr: 60 } }` | `nuxt.config.ts` | Incremental Static Regeneration (Vercel/Netlify). |
| `routeRules: { '/x': { headers: {…} } }` | `nuxt.config.ts` | Custom response headers. |
| `routeRules: { '/x': { redirect: '/y' } }` | `nuxt.config.ts` | Edge redirect. |
| `routeRules: { '/x': { appLayout: 'landing' } }` | `nuxt.config.ts` | Layer middleware calls `setPageLayout()` to switch layout. |
| `definePageMeta({ layout: false })` | page `.vue` | Bypass all layouts — page renders raw inside `<NuxtLayout>` slot. |
| `<ClientOnly>` | template | The shell SSRs; the wrapped subtree only mounts client-side. |

## Patterns from real-world consumers

### incubrain
- All 7 app pages use `definePageMeta({ layout: false })` — hand-built marketing pages.
- `routeRules['/internal/**'] = { robots: 'noindex,nofollow' }` for the team-only area.
- Content-driven URLs (`/sectors`, `/approach`) flow through the catch-all and fall through to `default`.

### astronera
- Uses `routeRules.appLayout` extensively: `/` → landing, `/blog/**` → article, `/team` → default, `/darksky/**` → docs.
- `/viirs/**` is `{ ssr: false, prerender: false }` — heavy client-side WebGL with a custom `viirs.vue` layout.
- Blog pages and pilot detail pages use `layout: false` for full-bleed presentation.

## Debugging

If a page renders wrong:

1. Run the playground matrix: `pnpm --filter playground test:e2e`.
2. Both `app/pages/foo.vue` and `content/pages/foo.md`? The app page wins.
3. `routeRules` precedence: multiple matching patterns merge in specificity order — check `.nuxt/dist/server/server.mjs` to see what Nitro applied.
4. Inspect the SSR HTML, not the hydrated DOM: `curl -s http://localhost:3000/foo` shows what the server emitted.

## Adding a test

Tests live in `playground/test/e2e/`. Add a fixture under `playground/app/pages/` (or `playground/content/pages/`), wire any required `routeRules` in `playground/nuxt.config.ts`, then add a `describe` block to `rendering.e2e.spec.ts`.

Each test covers one knob. Combinations are documented as scenarios above but not tested individually — if you hit a combination bug, add a targeted test for it.
