## Overview

Foundry is a Nuxt 4 layer. It does **not** invent its own rendering pipeline — every URL flows through one of Nuxt's stock paths. Understanding which path a given URL takes is the difference between a 200ms SSR'd marketing page and a 5MB SPA bundle shipped to a serverless function.

This page documents:

1. The order in which Nuxt resolves a URL → page component → layout → rendering mode
2. The four knobs you have (`app/pages`, content `[...slug].vue`, `routeRules`, `definePageMeta`)
3. The exact contracts the layer guarantees, all backed by tests in `playground/test/e2e/rendering.e2e.spec.ts`

Run the full matrix locally: `pnpm --filter playground test:e2e`.

## URL → page resolution order

For any URL, Nuxt checks in this order:

1. **`app/pages/<exact-path>.vue`** in your example app
2. **`app/pages/<dynamic>.vue`** in your example app (e.g. `[id].vue`)
3. **`layer/app/pages/[...slug].vue`** from Foundry — the content catch-all
4. **404**

The catch-all calls `useContentPage()`, which uses `useContentConfig().getCollectionForRoute(path)` to pick a Nuxt Content collection (mapped via `app.config.ts` → `content.routeMap`), then fetches the document via Foundry's `/api/_foundry/content/page` server endpoint.

**Takeaway:** an `app/pages/foo.vue` always wins over a `content/pages/foo.md`. Use app pages when you need Vue logic; use content when you want non-developers editing the page.

## Layout selection

Nuxt picks a layout in this order:

1. `setPageLayout('x')` called from a component or middleware
2. `definePageMeta({ layout: 'x' })` on the page component
3. **`routeRules: { '/foo/**': { appLayout: 'x' } }`** in `nuxt.config.ts` — bridged by the layer's global middleware `app-layout.global.ts`
4. The `default` layout

Foundry ships three layouts: `default`, `landing`, `article` (plus `docs` if the docs module is enabled). All three are **pure presentation** — they read from `useContentPage().context` and never fetch or throw. App pages can mount any layout without needing a sibling content file.

### Why content frontmatter `layout:` is not bridged

Putting `layout: landing` in a `.md` file does not change the rendered layout. Reason: by the time the layout component runs, the content document has not been fetched yet (the catch-all `<NuxtPage>` setup runs *inside* the layout's slot, after the layout's own setup). Bridging it would require a server-side pre-fetch in route middleware. For now, set the layout via `routeRules.appLayout` instead.

## Architecture: how content fetching works

Pre-fix, the catch-all called `queryCollection(...)` directly. That works in the browser via WASM SQLite but during SSR makes an internal HTTP roundtrip to `/__nuxt_content/<collection>/query` — which crashes under h3@1 + content@3.13 with `event.req.headers.entries is not a function`.

The layer now routes content fetching through its own server endpoints:

```
catch-all page
  ↓ useFetch('/api/_foundry/content/page?collection=X&path=Y')
  ↓ (during SSR: event.$fetch → handler directly, no real network)
layer/server/api/_foundry/content/page.get.ts
  ↓ @nuxt/content/server queryCollection(event, ...)
SQLite
```

Single code path. Server-only fetching. Client hydrates from Nuxt's payload. Side benefit: gives the layer a single observable boundary for caching, auth, and rate-limiting later.

## Rendering modes (the knobs)

| Knob | Where | Effect |
|---|---|---|
| `ssr: false` (global) | `nuxt.config.ts` | Whole app is SPA — no SSR anywhere. Foundry default is SSR. |
| `definePageMeta({ ssr: false })` | page `.vue` | Per-route SPA. Astronera uses this for `/viirs/**` (WebGL maps). |
| `routeRules: { '/x': { prerender: true } }` | `nuxt.config.ts` | Bake to static HTML at build time (SSG slice). |
| `nitro.prerender.routes: ['/x']` | `nuxt.config.ts` | Same as above; explicit list. |
| `nitro.prerender.crawlLinks: true` | `nuxt.config.ts` | Follow `<NuxtLink>`s during build and bake every reachable URL. |
| `routeRules: { '/x': { swr: 3600 } }` | `nuxt.config.ts` | Stale-while-revalidate cache. |
| `routeRules: { '/x': { isr: 60 } }` | `nuxt.config.ts` | Incremental Static Regeneration (Vercel/Netlify). |
| `routeRules: { '/x': { headers: {…} } }` | `nuxt.config.ts` | Custom response headers — used by incubrain for `/internal/**` noindex. |
| `routeRules: { '/x': { redirect: '/y' } }` | `nuxt.config.ts` | Edge redirect. |
| `routeRules: { '/x': { appLayout: 'landing' } }` | `nuxt.config.ts` | Bridged into `setPageLayout()` by the layer's global middleware. |
| `definePageMeta({ layout: false })` | page `.vue` | Bypass all layouts — page renders raw inside `<NuxtLayout>` slot. |
| `<ClientOnly>` | template | The shell SSRs; the wrapped subtree only mounts client-side. |

## Patterns from real-world consumers

### incubrain
- All 7 app pages use `definePageMeta({ layout: false })` — they're hand-built marketing pages.
- `routeRules['/internal/**'] = { robots: 'noindex,nofollow' }` for the team-only area.
- Content-driven URLs (`/sectors`, `/approach`) flow through the catch-all and fall through to `default`.

### astronera
- Uses `routeRules.appLayout` extensively: `/` → landing, `/blog/**` → article, `/team` → default, `/darksky/**` → docs.
- `/viirs/**` is `{ ssr: false, prerender: false }` — heavy client-side WebGL. The route also overrides the layout (`viirs.vue` in `app/layouts/`).
- Blog pages and pilot detail pages use `layout: false` for full-bleed presentation.

## Debugging

If a page renders wrong:

1. **Run the playground matrix.** `pnpm --filter playground test:e2e` tells you which contracts hold.
2. **Inspect `routeRules` precedence.** Multiple matching patterns merge in specificity order — check `.nuxt/dist/server/server.mjs` to see what Nitro applied.
3. **Check the resolution order.** Both `app/pages/foo.vue` and `content/pages/foo.md`? The app page wins.
4. **Inspect the SSR HTML, not the hydrated DOM.** `curl -s http://localhost:3000/foo` shows what the server emitted. Anything else is post-hydration.

## Adding a new test

Tests live in `playground/test/e2e/`. Add a fixture under `playground/app/pages/` (or `playground/content/pages/`), wire any required `routeRules` in `playground/nuxt.config.ts`, then add a `describe` block to `rendering.e2e.spec.ts` asserting the observable HTML.

The matrix is intentionally narrow: each test covers one knob. Combinations (e.g. "ssr:false + custom layout + dynamic params") are documented as scenarios in this page but not tested individually — if you hit a combination bug, add a targeted test for it.
