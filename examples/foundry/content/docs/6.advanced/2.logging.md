## Overview

Foundry uses [evlog](https://github.com/davestewart/evlog){target="_blank"} for structured logging. The key concept is **wide events** — one log entry per request that accumulates all context as the request progresses.

## Server-Side Logging

In server handlers, use `useLogger(event)` to get a request-scoped logger:

```ts
const log = useLogger(event)

// Accumulate context throughout the handler
log.set({ lead: { email: formData.email } })
log.set({ delivery: { platform: 'discord', status: 'sent' } })

// The wide event is auto-emitted at the end of the request
```

For errors, use `createEvlogError()` with `why` and `fix` fields for AI-readable diagnostics:

```ts
throw createEvlogError({
  statusCode: 400,
  why: 'Honeypot field was filled — likely bot submission',
  fix: 'Legitimate users should not see this error. Check for browser extensions filling hidden fields.',
})
```

## Layer Plugins

The layer ships two evlog plugins that run automatically:

### evlog-enrich

Adds user agent and geo data to every request's log context. Uses `createUserAgentEnricher()` and `createGeoEnricher()` from evlog.

### evlog-sampling

Ensures signal capture events are never sampled out in production. If a log entry contains `lead.email` or `delivery` in its context, it is always kept regardless of sampling rates.

## Drain Pipeline

Logs need a destination. Configure a drain in `server/plugins/evlog-drain.ts`:

```ts [server/plugins/evlog-drain.ts]
export default defineNitroPlugin((nitroApp) => {
  // Uncomment one of these:

  // Sentry
  // const drain = createSentryDrain({ dsn: process.env.NUXT_SENTRY_DSN })

  // Axiom
  // const drain = createAxiomDrain({
  //   token: process.env.NUXT_AXIOM_TOKEN,
  //   dataset: process.env.NUXT_AXIOM_DATASET,
  // })

  // PostHog
  // const drain = createPostHogDrain({
  //   apiKey: process.env.NUXT_POSTHOG_API_KEY,
  // })
})
```

The drain plugin is your responsibility to configure — the layer provides the infrastructure but doesn't choose a destination for you.

| Destination | Env Variable | Docs |

| [Sentry](https://sentry.io){target="_blank"} | `NUXT_SENTRY_DSN` | [sentry.io/docs](https://docs.sentry.io){target="_blank"} |

| OTLP (OpenTelemetry) | — | [opentelemetry.io](https://opentelemetry.io){target="_blank"} |

Use `createDrainPipeline()` for production setups with batching and retry.

## Browser Transport

Client-side `log.info()` and `log.error()` calls are automatically sent to the server via `POST /api/_evlog/ingest`. They flow through the same drain pipeline as server logs.

This is enabled by default in the layer config via `evlog.transport.enabled: true`.

## Production Sampling

In production, evlog can sample logs to reduce volume:

```ts [nuxt.config.ts]
evlog: {
  sampling: {
    rates: { info: 10, warn: 50, debug: 0 },  // Percentage
    keep: [
      { status: 400 },       // Always keep 4xx errors
      { duration: 1000 },    // Always keep slow requests
    ],
  },
}
```

The layer's `evlog-sampling` plugin ensures signal capture events (leads, webhook deliveries) bypass sampling entirely.
